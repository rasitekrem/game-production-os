# Claude Code adapter

Adapter id `claude-code` · format `claude-code-project/1` · code: `gpos/adapters/backends.py` (format only) on the shared [adapter layer](README.md).

## Compatibility target

These first-party documents were consulted on 2026-09-22 (implementation time only):

- [How Claude remembers your project](https://code.claude.com/docs/en/memory):
  - project instructions live in `./CLAUDE.md` (or `./.claude/CLAUDE.md`) and are loaded at session start;
  - keep them under about 200 lines;
  - while any `CLAUDE.md` exists in the working directory or above, Claude Code does not read `AGENTS.md` (the default setting; a user-level setting can make it read both);
  - **instruction layers are additive, and more specific instructions may take precedence**: `CLAUDE.local.md`, `CLAUDE.md` files in parent directories and in subdirectories (loaded as Claude works there), `.claude/CLAUDE.md` and `.claude/rules/*.md` all add persistent instructions.
- [Skills](https://code.claude.com/docs/en/skills):
  - project skills live in `.claude/skills/<name>/SKILL.md`, discovered from the session directory and its parents up to the repository root;
  - `description` is always in context, and the body loads when the skill is used;
  - keep `SKILL.md` under 500 lines; supporting files load only when referenced;
  - **a skill with the same name at a higher scope (enterprise, personal) shadows the project skill.** GPOS therefore generates project-scoped names, `gpos-<namespace>-<skill>`.

Claude Code 2.1.220 was installed at implementation time. The adapter renders and syncs files; it does not run Claude Code.

## Generated files

| File | Content |
|---|---|
| `CLAUDE.md` | concise operating contract (budget 8,000 characters / 200 lines) |
| `.claude/skills/gpos-<namespace>-<skill>/SKILL.md` | one skill per enabled GPOS specialist; front matter `name` (the scoped id) and `description` |
| `.claude/skills/gpos-<namespace>-game-director/references/workflows/*.md` | workflow contracts, read when routing |
| `.game/gpos-generated/claude-code/manifest.json` | ownership, provenance and semantic parity |

Skills are invoked by domain intent, or directly with `/gpos-<namespace>-<skill>`.

## Ownership

- A human-written root `CLAUDE.md` is never overwritten or adopted: sync stops with `UNOWNED_ENTRYPOINT`.
- Any other project-local instruction layer GPOS does not own stops sync and is reported by check (`INSTRUCTION_LAYER_CONFLICT`). This covers `.claude/CLAUDE.md`, `CLAUDE.local.md`, a `CLAUDE.md` in any subdirectory, `.claude/rules/*.md`, and an `AGENTS.md` not generated by GPOS. It also covers such files above the project up to the git repository root. They are never edited.
- Project `.claude/settings.json` or `.claude/settings.local.json` with a non-empty `claudeMdExcludes` stops sync and is reported by check (`INSTRUCTION_CONFIG_CONFLICT`); unreadable settings fail closed. Other settings are ignored. Settings are never edited.
- A project skill (root or nested `.claude/skills/`) with a generated GPOS skill id is a `SKILL_ID_CONFLICT`.
- Other skills in `.claude/skills/` are never touched.
- No hooks, settings, plugins or user-level (`~/.claude`) files are generated.

## Limitations

- A project that already relies on a human-written `CLAUDE.md` must move or merge it by hand before syncing. Phase 2B has no adoption command.
- Phase 2B does not merge or adopt other instruction layers: a project using them must move their content into `.game/` authority first.
- User-level (`~/.claude`), enterprise and managed instructions and settings are outside the project and are not inspected: a documented trust boundary. GPOS guarantees project-local consistency only.
- `RUNTIME_NOT_YET_SMOKE_TESTED`: the files have not been loaded in a live Claude Code session; that belongs to the real-agent pilot.
- If both adapters are synced, Claude Code reads `CLAUDE.md` and not the Codex `AGENTS.md` (default setting), so the operating contract is not loaded twice.
